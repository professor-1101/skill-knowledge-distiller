# compile (R8) — render a skill package

Role: compiler. Source access: **no**.

A compiler able to reach the source will fill gaps from it instead of reporting
them, turning a measurable deficiency in the store into an invisible one and
defeating the certificate. If a skill cannot be written from the store, that is
a finding.

## Procedure
**S1 Boundary.** One concept cluster, one skill. Confirm it maps to a
recognisable class of task rather than to a chapter. A skill named after a
chapter has failed before it is written.

**S2 Description first, as a design instrument.** If you cannot write one crisp
trigger sentence, the boundary is wrong — go back to S1. Then **discard the
draft and rewrite it last**, from the finished body, and trigger-eval it. The
first writing tests the boundary; the second is the product.

Name the *symptoms* a user would describe, not only the vocabulary they might
use. The reader who has the problem but not the term is where a skill is most
valuable and least likely to fire.

**S3 Body**, against the canonical template in `docs/compiling-skills.md`.

**S4 Split.** Over budget, move evidence, extended examples and long analysis
into `docs/`, with a pointer saying when to read each. Contested questions stay
in the body — burying a live disagreement is the flattening R7 forbids.

**S5 Scripts** only where a deterministic procedure would otherwise be
rewritten on every invocation.

**S6 Grounding.** Every rule resolves to claims, which resolve to locators.
Unresolvable means fabricated: rejected, not fixed.

**S7 Lint. S8 Trigger eval. S9 Task eval.**

## Output
```
skills/<gerund-name>/
  SKILL.md
  docs/evidence.md      rule -> claim -> source locator
  docs/examples.md      claims dispositioned `supporting`
```
Gerund form — `selecting-a-technique`, not `technique-selection` — because the
gerund names the activity the model matches a live task against.
